# 시제품 v3 기록 (2026-11-05)

> v3는 **모든 평가 세트(E2 개발·E2b·합성, E1)의 결과를 본 뒤** 만든 개발판이다. 제안서의 정확도는 v2 값(E2b 시험 A, E1 (A)·(C))을 그대로 쓴다. v3의 효과는 '경계 사례 점검'과 '같은 사례에서 나빠지지 않음'으로만 보인다.

## 1. 바뀐 것

| 항목 | 내용 | 왜 |
|---|---|---|
| 중복·보충 조건 대조 | 고른 유형의 '중복·보충 조건'(29개 유형)을 사업안이 어긴다는 근거가 원문에 있으면 '위반'이고, 순서도에서 일반으로 간다(사람 판정판과 같은 순서). 근거 구절은 원문과 대조한다 | 합성 S3(응시료에 운전면허 포함)에서 신속을 잘못 권했다 |
| 지역 조건 대조 | 유형 칸에 지역 조건이 있는 17·33·48번만 LLM이 사업안이 그 조건을 충족하는지 본다. 밖이면 밖, 확인불가면 보류 | 합성 S5(인구소멸지역 아님)에서 신속을 잘못 권했다 |
| 유사사업 AI 판정·지역별 묶음(C′) | 후보 = TF-IDF 상위 30 ∪ 태그+키워드 상위 30 ∪ 같은 지자체·광역 본청 낱말 겹침 상위 20. AI가 동일·유사·무관과 근거를 낸다. 결과는 같은 지자체 / 같은 광역 본청 / 같은 시도 / 다른 시도(앞 5건, 나머지 건수)로 묶는다 | E1: 필수 비교 대부분이 다른 시도의 같은 사업이고, 중복 확인이 필요한 가까운 지역 후보가 묻혔다 |
| 공용 모듈 | `scripts/similar.py`: E1 측정(`run_e1_eval.py`)과 시제품이 같은 판정 함수를 쓴다. 측정에 쓴 지시문은 글자 하나 바뀌지 않았다(비교 확인) | 측정과 시연이 같은 엔진이어야 한다 |
| 모델 명시 | `llm.py`가 `-m gpt-6.1-sol`을 넘긴다. 캐시 키에 모델 꼬리표를 붙인다 | 11/5 Codex 설정 기본값 `gpt-6-astra`가 이 계정에서 지원되지 않았다. 11/3 측정은 -m 없이 설정 기본 모델로 돌았다(gpt-6-astra 추정, 기록 없음) |

- 쓰는 법: `consult_prep.py ... --v3`. E2 평가처럼 유사사업 판정이 필요 없으면 `--skip-similar`를 붙인다.

## 2. 첫 v3 판의 실패와 v3.1

첫 판은 숫자 규칙(중위소득·수급·연령)이 못 읽는 **모든** 대상 조건을 LLM이 대조하게 했다.
- LLM이 거주 요건처럼 대상을 좁히는 조건까지 '밖'으로 봤다.
- 그래서 개발 세트에서 신속 사례 428·429·474를, E2b에서 838을 틀렸다. 유형판정은 개발 23→21/29가 됐고, 대상 정확도는 개발 8/8→6/8, E2b 5/5→3/5로 떨어졌다.
- 그 출력은 `data/processed/*_runs/M3_v3first/`에 남겼다.

v3.1은 LLM 대상 대조를 **유형 칸에 지역 조건이 있는 세 유형**에만 쓴다. 이 범위는 사례가 아니라 유형 표의 글자로 정한다. 지시문은 그대로라 LLM을 다시 부르지 않고 캐시로 다시 채점했다.

## 3. 결과(모두 개발 점수)

| 세트 | v2(11/3 모델) | v2(새 모델, M2n) | **v3.1(새 모델, M3)** | 바뀐 사례 |
|---|---:|---:|---:|---|
| 합성 11건 유형판정 | 5/11 | 5/11 | **7/11** | S3·S5 → 일반(정답). 신속을 잘못 권한 사례 2 → **0** |
| E2b 20건 유형판정 | 17/20 | 17/20 | 17/20 | 없음 |
| 개발 29건 유형판정 | 23/29 | 23/29 | 23/29 | 없음 |

- **모델이 바뀌어도 v2 판정은 그대로였다.** 새 모델이 실제로 새로 판단했지만(이유 문장이 20건 모두 다름) 60건의 판정 칸이 모두 같았다. 그래서 11/3 측정값을 새 모델 시제품의 값으로 써도 무리가 없다.
- 합성에서 남은 오류 4건
  - 3건은 구간별·비율 상한을 계산하지 못해 보류로 넘긴 것이다(S1·S8·S9). 안전한 쪽이다.
  - S11은 정보가 너무 적은 사례다.

### E1(유사사업)

| 지표 | v2 지시문(11/3 모델) | v3 지시문(보완 문구, 새 모델) |
|---|---:|---:|
| (A) 정밀도 / 재현율 / F1 | 90% / 90% / 0.90 | 89% / 90% / 0.90 |
| (C) 같은 지자체·광역: AI 양성 중 실제 필수 비교 | 5/15 | 5/14 |
| (C) 같은 지자체·광역: AI 무관 중 실제 필수 비교 | 0/15 | 0/16 |

- 보완 문구('같은 지자체라는 이유만으로 유사로 보지 않는다')는 효과가 거의 없었다.
- 이 묶음에서 AI는 놓치지 않는 대신 넓게 고른다. 중복 확인에서는 이쪽이 안전하다. 그래서 시제품은 이 묶음에 '반드시 원문 확인'을 붙여 보여 준다.

## 4. 시연 예시

- `30_analysis/시제품_예시/v3_393_구미_청년전월세이자.md`: 구미시 청년 전월세보증금 대출이자 지원(변경)
  - B: 유형 37번, 대상 확인불가(소득 기준을 중위소득 %로 확인 못 함), 상한 안 → 확인불가. 중복 위반 근거 없음
  - C′ 같은 지자체 3건
    - 기존 사업(동일)
    - 청년월세 지원(유사, E1 (C)에서 사람이 확인한 풀 밖 발견)
    - 청년근로자 행복원룸(유사)
  - C′ 다른 시도는 같은 사업 45건 중 앞 5건만 표시한다.

## 5. 제안서에 쓰는 법

- 정확도 숫자는 v2 값(E2b·E1)을 쓴다. 측정 뒤에 정답 없이 고친 부분은 경계 사례 점검으로만 쓴다.
  - 예: "제안자가 만든 경계 사례에서 중복·보충 조건과 지역 조건을 놓쳐 신속을 잘못 권한 2건을 찾아, 조건 대조를 더해 고쳤다. 실제 사례 49건의 판정은 바뀌지 않았다."
- 첫 v3 판의 실패(모든 대상 조건을 LLM에 맡기면 실제 사례에서 나빠짐)도 개발 과정으로 쓸 수 있다.
